Tick Sampling: 4 samples/sec (every 16th tick)

Store only alive players. Player positions change meaningfully at ~0.25s intervals. Kills/bomb events still have exact tick precision from event tables. This gives 63M rows vs 1.26B at full rate — 20x reduction.

Flexibility for Map Control Experimentation

The raw ticks table stores positions + health + weapon — the exact inputs to any map control algorithm. Different algorithms (BFS depth, sightline-aware, weapon-weighted) can all be computed from the same stored data without re-parsing. Pre-computed results go in tick_map_control with an algorithm column.

Agent Orchestration System

A YAML-driven system for running multiple Claude Code agents with validation gates, parallel execution, and human checkpoints.

Task Spec Format

task:
  id: "nav-cache"
  name: "Cache Nav Mesh Loading"
  writable_files: ["awpy/stats/map_control.py", "tests/test_map_control.py"]
  gates:
    pre:  [{type: unit_test, command: "uv run pytest ...", expected: "passed"}]
    post: [{type: unit_test, ...}, {type: performance, ...}]
  prompt: "Add _nav_cache dict and _get_nav() helper..."
  max_iterations: 5
  stuck_threshold: 3
  depends_on: []
  parallel_safe_with: ["config-dataclass", "kill-distance"]
  isolation: "shared"  # or "worktree" for file-conflict isolation

Agent Loop Pattern

while iterations < max_iterations:
  1. Run pre-validation (must pass or abort)
  2. Invoke Claude Code CLI: claude --print --max-budget-usd 2.00
  3. Run post-validation gates
  4. If ALL pass → DONE
  5. If fails → include failure context in next prompt, retry
  6. If stuck_threshold consecutive failures → ALERT HUMAN

Utility (Smokes/Molotov/Flash) Research

Utility Integration: Smokes, Molotovs, Flashes

Currently BFS propagates freely through smokes and molotovs — a player behind smoke shows as controlling the area beyond it.

Core Design: Pre-BFS Block + Post-BFS Override

  1. Pre-BFS: Smoked tiles and enemy-molotov tiles block BFS propagation (one-line change in _bfs_helper: neighbors - seen - blocked_tiles)
  2. Post-BFS: Override smoked tiles → 0.5 (neutral), molotov tiles → thrower's team (0.0 or 1.0)

Smoke Integration

AspectDesign
DetectionTiles whose centroid is within 144 units of smoke (x,y,z) + Z tolerance ±128
BFS effectBFS cannot propagate through smoked tiles (blocks both teams)
Tile value0.5 (neutral) — neither team controls smoked area
VisualizationGrey overlay, higher opacity than regular tiles
One-way smokesIgnored in v1 (needs raycasting + geometry)
Data sourcedemo.smokes: entity_id, start_tick, end_tick, X, Y, Z

Molotov Integration

AspectDesign
DetectionTiles within 96 units of inferno position, Z tolerance ±64
BFS effectBlocks enemy BFS only (T molotov blocks CT BFS, not T BFS)
Tile valueForced to thrower's team: T molotov → 0.0, CT molotov → 1.0
VisualizationOrange overlay for T molotov, blue for CT molotov
Data sourcedemo.infernos: entity_id, start_tick, end_tick, X, Y, Z, thrower_steamid

Flash Integration

Reduce flashed player's BFS source value: starting_value = max(0, 1 - flash_duration/2.0)

Fully blind (flash_duration ≥ 2s) → zero map control. Partially blind → proportional reduction.

Data: flash_duration column already available in tick data.

HE Grenades

Skip in v1. Instantaneous effect, very brief threat zone (~0.5s). Impact on map control is minimal. Revisit if needed.

Priority/Interaction Rules

Molotov overrides smoke (fire burns through smoke in CS2). Smoke overrides regular BFS. Two opposing molotovs on same tile → 0.5 (neutral).

Active Utility State Tracker

@dataclass(frozen=True)
class ActiveUtilityState:
    smoke_blocked_tiles: frozenset[int]
    t_molotov_tiles: frozenset[int]     # T-thrown molotovs (blocks CT BFS)
    ct_molotov_tiles: frozenset[int]    # CT-thrown molotovs (blocks T BFS)

    @property
    def t_blocked(self) -> frozenset[int]:
        return self.smoke_blocked_tiles | self.ct_molotov_tiles

    @property
    def ct_blocked(self) -> frozenset[int]:
        return self.smoke_blocked_tiles | self.t_molotov_tiles

Weapon from Data Research

Deriving Optimal Weapon BFS Depth from Data

Instead of hand-tuning BFS depth per weapon, learn it from professional match data.

Approaches (Recommended Order)

ApproachMethodData SourceComplexityVerdict
1. Kill Distances95th percentile of Euclidean kill distance per weapon class → convert to BFS hops via avg edge distancedemo.kills (attacker/victim X/Y/Z, weapon)LowSTART HERE
3. Damage DistancesDamage-weighted 95th percentile of engagement distances. Larger sample than kills.demo.damagesLowDO IN PARALLEL
2. Damage Decay CurvesReplace linear BFS decay with weapon-specific exponential: threat = base × range_mod^(dist/500)CS2 weapon tables + damagesMediumBest long-term architecture
5. Player BehaviorTrack avg distance-to-nearest-enemy when player is stationary with each weapon typeTick data + velocity + weaponHighCross-validation signal
4. Round Outcome OptimizationGrid/Bayesian search over depth params, maximize AUC of map control predicting round winnerEverything above + round outcomesVery HighGold standard — do last

Key Formula: Distance to BFS Depth

kill_distance = sqrt((ax-vx)² + (ay-vy)² + (az-vz)²)
avg_edge_dist = sum(edge_dist for all nav edges) / num_edges  (~100-150 units on dust2)
bfs_depth(weapon) = round(percentile_95(kill_distances[weapon]) / avg_edge_dist)

Implementation Note

Multi-Channel Encoding Research

Multi-Channel Spatial Game State Encoding

Core idea: Instead of one BFS-based map control layer, create multiple independent channels — one per game concept. Don't prescribe how they interact; let the model learn it.

Why NOT BFS for Everything

Weapon threatRaycasting / directional coneAWP threatens along sightlines, not graph blobs

Smoke denialEuclidean sphereSmoke is physical radius, ignores nav graph
EconomyPoint value, no spreadMoney doesn't spread geographically
FlashEuclidean radius + durationPhysical blast, not graph phenomenon
VelocityDirectional vectorMovement is per-player, not area-based

The Better Design: Raw Values + Learned Interaction

Encoding (cheap, deterministic): Place raw values at player tiles. No spread. No BFS.

Interaction (learned): Model's attention/GNN layers learn the spread pattern per channel from data.

Recommended Architecture: Hierarchical

Raw tick data

  • Learned spread patterns: Look at attention from a player's tile — if it forms a cone aligned with yaw, the model learned directional threat
  • Comparison with hand-coded BFS: Where do they disagree? Those are the model's novel insights

IGL Model Research

IGL Navigation Model: Data-Driven In-Game Leader

Given current map control state (or sequence of recent states), suggest what the team should do next.

Step 1: Win Probability Foundation

Start with win probability, not action prediction.

The label is unambiguous (round has a winner), requires no manual annotation, and serves as the foundation for everything else. Once you have win probability, you evaluate actions by: "does this increase our win prob?"

Entirely extractable from tick data without BFS. The single mc_metric can be added at 1/sec sampling as supplementary.

Strategy Clustering

Cluster 5-player position configurations into ~20-50 "formations" via K-means. Clusters naturally correspond to strategies ("5-man B rush", "A-split with mid control", "default spread"). Label clusters once manually. "Next action" = cluster ID at t+5sec.

Validation

  • Split by match (not round) — 120 train / 20 val / 20 test
  • Calibration curves — "65% win" must mean roughly 65%
  • Backtesting — find rounds where model was most surprised (high P but lost), generate GIF, sanity check
  • Cross-map model with learned map embedding (pools all 300K snapshots vs splitting per map)

Data Volume

160 demos → ~3,840 rounds → ~300K snapshots at 1/sec. ~110 MB as float32. Trains MLP in minutes on laptop.

Fog of War Research

Fog of War — Information Asymmetry in Win Probability

Current WP models use "god view" — all 10 player positions visible. In reality, each team only sees spotted enemies.

Core Question

How much does perfect information inflate WP accuracy? If god-view AUC >> team-perspective AUC, then hidden information is the dominant factor in round outcomes, meaning map control (as information gathering) is even more valuable than we thought.

Feature Construction: T-Perspective

For each CT player at tick T:
  If spotted == True:       use actual X/Y/Z (known position)
  If spotted recently (<5s): use last-spotted position + staleness feature
  If never spotted:          encode as "unknown" (zero vector or prior)
  CT health:                 only known if spotted, else assume full (100)
  CT weapon:                 only known if spotted, else assume rifle

Available data: m_bSpotted (bool per player per tick) confirmed in demoparser2. Place names from radar are the natural representation for partial info.

Connection to Multi-Channel Design

The "presence" channel should have TWO variants: actual positions (for training label) and spotted-only positions (for team-perspective models). The gap between them IS the information asymmetry.

Place Mapping Done

Tile-to-Place Mapping — Self-Improving System

100% coverage achieved on dust2 (10 demos, 504K samples, 24 regions). System designed to learn incrementally as more demos are parsed.

How It Works

Demo parse → extract (X,Y,Z, last_place_name) per tick
  → cKDTree nearest-neighbor → nav area ID
  → accumulate vote: area_id → place_name += 1
  → merge into persistent mapping file
  → if coverage > 70% and 3+ demos: BFS gap-fill
  → bump version if any tile's winner changed

Cross-demo accuracy: 96.3%. Average confidence: 0.97. Only 15 low-confidence tiles (all at legitimate region boundaries).

Incremental Learning Architecture

ConceptDesign
Storage~/.awpy/place_mappings/{map_name}.json — one file per map, auto-created
Merge strategyAdditive vote accumulation — never discard historical data
ConfidenceBayesian-smoothed: (winner_votes + 10) / (total_votes + 20) — needs ~20 votes to stabilize
Versioningmajor.minor.patch — major bumps when >5% of tile winners change (possible game update)
LifecycleEMPTY → PROVISIONAL (1-4 demos) → STABLE (5+ demos, >90% consistency) → STALE (patch change or >90 days)

ETL Integration Hooks

  1. On each demo parse: Extract votes, detect anomalies, merge, log coverage
  2. After 3+ demos (>70% coverage): Trigger BFS gap-fill
  3. On CS2 patch update: Flag all mappings as potentially stale
  4. CLI: awpy place-mapping status de_dust2 — show coverage, version, anomalies

Multi-Map Bootstrap

For a new map: auto-detect from demo header → create empty mapping → accumulate votes → BFS fill at 70% → promote to STABLE at 5 demos + 90% consistency. Works automatically for any map with a nav mesh.

Key Design Decisions

  • Never auto-delete data — a stale 10K-vote mapping is better than no mapping
  • cKDTree for speed — O(log n) lookups, processes 500K samples in <0.1s per demo
  • BFS fill at 70% threshold — enough anchor points for accurate extrapolation
  • Store full vote distribution per tile — enables retroactive analysis and drift detection
